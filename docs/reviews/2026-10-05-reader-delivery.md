# 报告阅读体验优化

这次优化的目标是让报告先回答人的问题：项目做什么、事情如何发生、最后得到什么、哪些内容还不能确定。通用报告模板、中文示例和写作规则已同步更新。

## 直接体验

在仓库根目录运行：

```sh
node scripts/build.mjs examples/order-journey/atlas.json --replace
```

双击打开 `examples/order-journey/report.html`。它无需网络或本地服务器，包含“提交一笔购买”和“取消一笔订单”两个中文场景。示例来自同目录合成源码，明确说明订单只保存在内存中，付款和发货尚未被证实。

## 阅读体验的变化

| 读者想知道什么 | 页面现在怎样回答 |
|---|---|
| 这个项目做什么 | 首页先给业务摘要，再提供流程、结论和依据三个阅读入口 |
| 我关心的事如何完成 | 业务场景放到关系图之前；按开始条件、处理步骤和最终结果阅读 |
| 哪些结论值得注意 | 结论卡片展示业务影响与后续确认问题，不只列标题和状态 |
| 各部分负责什么 | 模块卡片直接展示职责句子，不必点开才能理解名称 |
| 这些部分有什么联系 | 协作区域使用日常中文，移除实现字段和英文算法术语 |
| 这个结论有什么依据 | 文件位置默认折叠；需要时展开，进入代码后可以返回原阅读位置 |
| 哪些地方还不知道 | 流程中的未知结果单独提示，保留继续核验的具体方向 |
| 手机能否舒服阅读 | 加大正文和阶段标题、控制行宽、减少重复标题，调整链接位置及窄屏布局 |

关系图仍然可用，但不再独占首页的主要位置。源码内容保持准确，减少的是正文中的技术噪声，并非证据或业务边界。

## 后续报告也沿用同一标准

[读者体验与表达约束](../../references/reader-experience.md) 已接入技能指令、清单说明、分析指南和可复制提示词。要求报告作者把业务含义写进显示标题与摘要，把函数名、路径和内部标识保留在定位细节中。

例如，阶段标题写“有货才预留，没有货就说明原因”，正文解释库存不足时不会创建订单；读者展开依据后仍能找到准确实现。生成器不会凭函数名称自动猜测业务含义。

已有清单可以继续使用。重新生成 HTML 后即可采用新的模板；如果原清单的标题和摘要本身只是函数名或代码转述，还需要结合源码改写这些显示内容。旧的独立 HTML 文件不会自行更新。

## 实际验证

- 人工查看新版桌面首页、完整流程和手机流程截图，检查阅读顺序、标题重复、正文大小与未知项呈现。
- 新增阅读场景验收在 Chromium、Firefox、WebKit 全部通过，覆盖首页入口、业务步骤、按需证据、返回路径，以及 390px/320px 布局。
- 原有普通报告、复核预览、已接受版本在三种浏览器中的 9 组验收全部通过。
- 46 项自动化测试与端到端回归通过；40 个 JavaScript 文件语法和 64 个本地文档链接检查通过。

本次浏览器验证使用 Windows 上的浏览器引擎，不等于真实手机设备验收。用于人工观察的临时预览服务不属于交付依赖，独立文件打开已另行验证。
