评估日期：2026-10-05。对象：当前工作区代码。方式：静态检查、现有测试、独立夹具复现与合成规模基准。

## 结论

**项目已具备较完整的可用闭环，但还不能认为已经完善，仍有明确的优化空间。**

按“本地运行、由人或 AI 编写清单、生成有源码依据的离线架构报告”的定位，它已经超出概念验证阶段：清单校验、报告生成、增量更新、复核、版本接受和交付检查均有实现。最值得保留的是证据定位、失效识别、离线交付和显式复核这些基础设计。

当前优先事项应是补齐新增命令的正确性和防覆盖保护，其次才是规模性能、使用体验与代码拆分。本次已复现两个现有测试未覆盖的问题，其中一个可能覆盖用户输入清单，另一个会遗漏业务配置变更。

没有必要推倒重写，也不建议仅凭功能数量继续扩张。先把已有能力做得一致、可靠，更有价值。

## 优先修复：两个已复现问题

### P1：compare 的输出可以覆盖输入清单

位置：[scripts/compare.mjs:88](../../scripts/compare.mjs#L88)。

该命令直接调用 `writeFile(resolve(options.output), ...)`，没有复用其他命令的输出路径规划和原子写入保护。

在独立测试清单上执行：

```text
node scripts/compare.mjs base.json head.json --output base.json
```

实际结果：退出码为 0，`base.json` 被替换为 `purpose: "repo-atlas-semantic-diff"` 的差异报告，原清单内容丢失。本次只操作了专门创建的临时夹具，没有覆盖实际项目清单。

建议：复用 `io-lib.mjs` 的路径和写入机制，始终保护两个输入文件；已有输出默认拒绝覆盖，明确提供替换选项；检查符号链接/目录联接及真实路径，并使用原子写入。

验收：输出等于任一输入、输入的链接别名、已有文件、写入失败等情况都应有回归验证，且失败后原文件字节保持不变。

### P1：compare 会漏报任意 JSON 配置中的同名业务字段

位置：[scripts/compare.mjs:26](../../scripts/compare.mjs#L26)，尤其递归 `clone()` 的字段排除逻辑；契约见 `schemas/atlas.schema.json` 中 `$defs.flag.properties.value`。

`flags[].value` 允许任意 JSON，但 `clone()` 在所有递归层级都会过滤 `workspace`、`output`、`update`、`review`、`$schema` 及部分运行期字段，没有区分这些名称所处的语义位置。

使用两个通过结构校验的清单，仅修改同一个 flag 的业务值：

```json
{"output":"before","workspace":"before","update":1}
```

改成：

```json
{"output":"after","workspace":"after","update":2}
```

实际结果：比较成功，`summary.changed` 为 0，`collections.flags.unchanged` 为 1。这会让读者遗漏真实配置变更。

建议：按字段路径或实体类型排除运行期元数据；对 `flags[].value` 保留完整业务值。不要使用对所有 JSON 对象都生效的字段名黑名单。

验收：顶层或实体级运行期字段按契约忽略；业务值中同名字段以及嵌套对象、数组内的变化均能识别。

CLI 的一个具体复现：`compare.mjs --json base.json head.json` 返回用法错误、退出码 2，因为解析器把第一个文件名当成 `--json` 的值。文档展示的“参数放在末尾”形式可以工作，所以这项归类为一致性/体验问题，不与前面两个正确性问题同级。

优化目录扫描时，必须保留不同 fileGroup 的独立后缀和排除规则，避免为去重而漏扫。当前哈希阶段已经使用最多 8 个并发任务，不能简单把问题描述成“完全没有并发”。

### 合成规模基准

运行 `node scripts/benchmark.mjs --scales 1000,10000`，退出码 0。

环境：Windows，Node v24.3.0。时间：2026-10-05T03:04:41.073Z。

| 指标 | 1000 文件 | 10000 文件 |
|---|---:|---:|
| 证据引用数 | 12 | 12 |
| 冷快照 | 705 ms | 6289 ms |
| 热快照 | 543 ms | 4567 ms |
| 构建 | 1361 ms | 11412 ms |
| 增量差异 | 1598 ms | 13036 ms |
| 增量上下文 | 1803 ms | 13812 ms |
| 快照进程采样峰值 RSS | 94 MiB | 132 MiB |
| HTML 大小 | 3911160 字节 | 4775156 字节 |
| 上下文大小 | 7021 字节 | 57215 字节 |
| 上下文发生截断 | 否 | 否 |

这说明增量上下文体积控制已有实际效果，但大目录的本地处理仍需数秒至十余秒，有优化价值。基准仅为每种规模一次采样：合成小文件、12 条证据、1% 未引用文件发生变化、没有 Git 历史；RSS 仅覆盖快照进程，不是所有子进程的总峰值。不能据此承诺任意真实万文件项目的性能，也不能与旧结果简单比较后认定性能退化。
