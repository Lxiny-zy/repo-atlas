# 关系分析的证据与取舍

## 先确定层次

| 层次 | 需要回答 | 可读证据 |
|---|---|---|
| 产品和业务 | 角色如何进入、完成什么事 | 页面、路由、CLI、API handler、消息消费者 |
| 业务职责 | 谁创建、校验、更新和读取业务事实 | 服务实现、编排器、领域对象、调用点 |
| 部署与基础设施 | 哪些进程独立运行、如何连接 | 构建清单、容器/启动配置、任务注册、客户端构造 |
| 持久化 | 当前值、快照、行为记录放哪里 | SQL、ORM mapping、迁移、对象存储或事件实现 |

不要把源码目录画成已部署服务，也不要把文档中的未来组件放进现有调用主链。边的方向服从该图的定义：`A 调用 B` 与 `B 返回数据给 A` 可以分别成立；说明图中表示哪一种，不画没有语义的双向箭头。

## 先建覆盖账本

覆盖矩阵用于暴露本次分析的边界，不用于给项目打分。先从用户目标和仓库形态选择相关维度，再随阅读进度更新状态。常见维度及最低证据如下：

| 维度 | 最低确认内容 | 常见证据 |
|---|---|---|
| 入口与角色 | 谁从哪里触发什么动作 | 页面路由、API 注册、CLI、消费者注册 |
| 认证与授权 | 身份在哪里建立，权限在哪里强制 | 中间件、策略检查、服务端 guard |
| 主业务链 | 入口到最终写入或结果的完整调用 | handler、服务调用点、写入实现、下游读取 |
| 状态与数据 | 当前事实、历史、计划、结果分别存放在哪里 | 模型、迁移、查询、序列化和约束 |
| 异步与外部副作用 | 消息、任务和外部调用的发起与消费 | producer、worker 注册、客户端构造、回调 |
| 失败与恢复 | 错误、超时、重试、补偿和人工恢复 | catch 分支、重试策略、死信、状态迁移 |
| 一致性与并发 | 事务、幂等、版本、锁和唯一约束 | transaction、幂等键、版本字段、索引 |
| 配置与环境 | 默认值、覆盖顺序和有效范围 | 配置加载器、启动参数、部署清单 |
| 部署与运行 | 独立进程、连接关系、健康检查和定时任务 | Docker、Kubernetes、systemd、任务注册 |
| 可观测性 | 日志、指标、追踪与审计能回答什么 | logger、metrics、trace、audit writer |
| 测试保障 | 哪些主链和失败分支有可执行验证 | 测试入口、fixture、CI 配置、本次执行结果 |

`covered` 表示本次范围已有足以支撑结论的证据；`partial` 表示读到部分实现但仍有影响判断的缺口；`unknown` 表示尚无证据；`not_applicable` 表示该维度与项目或本次范围无关。不要把“搜到关键词”记为已覆盖。

## 追一条真正的业务链

从一个实际入口读到最终写入，再追读取者。对会改变业务事实的动作，确认：

- 谁能做，代码在哪里验证身份和权限；前端按钮隐藏与后端授权分别记录。
- 读取哪些字段，以什么状态、版本或唯一键检验输入。
- 哪个服务实际写入哪些对象；旧表、新表和只被清理器提到的表如何区分。
- 数据库事务在哪里开始/结束，外部 API 在事务内还是事务外。
- 如何处理重复、并发、部分成功、结果未知、重试；未实现的能力不得画成已经兜底。
- 下游凭当前值、确认快照还是实际结果继续工作。

这些问题用于选择需要深入的节点，不要求每个低风险辅助方法都有一段完整报告。

## 提炼结论与未知

把能改变读者判断的内容放入发现项，而不是把所有观察都提升为结论：

- `fact`：由当前实现直接确认，例如“请求只入队，不等待生成完成”。
- `decision`：代码或约束体现出的明确取舍，例如“报告依赖固定版本资源以保证离线可复现”。
- `risk`：当前实现造成的具体失败或运维暴露，需要说明影响，不做泛化安全审计。
- `gap`：本次证据缺口或实现缺口，需要给出最短验证路径。

可信状态与类型分开。`confirmed` 要有直接实现证据；`inferred` 要说明推理链并引用两端证据；`unverified` 不写成事实，必须给出下一步检查位置。旧文档与当前代码冲突时，将旧文档标为历史或规划来源，以当前核对过的代码描述现状。

## 数据关系

只列该范围相关的数据对象。关系至少能回到“左对象.键 ↔ 右对象.关联属性”；基数有唯一键或实现证据才画确定的一对一。父记录没有子记录、关联字段可空、跨库逻辑关联、逻辑删除和版本匹配都可能改变基数。

快照与冗余需要解释保留的历史事实和读取用途。业务当前状态、外部实际结果、计划节点、文档资产和审计事件是不同事实，不因名称相近合并。

没有数据库时，用文件、集合、缓存键、消息、队列和对象关系表达，不创建一套虚构 ER 模型。

## 索引的证据等级

- 文件计数：清楚说明扫描了哪些目录、排除了哪些产物。
- 对象名引用：只能证明文本出现；实体、DDL、查询、写入、注释和清理引用的含义不同。
- 接口映射：检查实际注册机制。动态路由、反射或中间件不可只按函数名推断 URL。
- 配置开关：标出来源文件与默认值/覆盖关系；源码中的生产配置不是现场有效值。
- 测试：区分读过测试、执行通过、跳过和环境限制，历史测试结果不冒充本次验证。

## 视觉复核

总览保留核心业务环节与主要依赖，通常十几个节点比塞入所有类更有用，但不设机械上限。节点过密时按职责或事件拆图，并让侧栏切换和模块索引连接视图。

图下说明解释关系的意义，例如“创建任务只排队，生成动作才产出文档”；不要复述节点文字。颜色和线型含义需要图例，规划与待确认关系不能只靠颜色区分。

复杂长图允许更高画布、缩放和拖动。手机入口可提供纵向简图，但不得移除影响理解的条件。细节可放在节点弹窗，保留真实字段和源码链接。

第一屏不是封面。它应同时给出项目名称、当前视图、分析基线、证据规模和最重要的系统关系。索引页应让读者从发现项或覆盖缺口反向进入模块与源码，而不是只能按文件名浏览。

最终人工对账至少抽查：

- 总览中的每条关键边能否回到模块或视图证据。
- 发现项的状态、影响和证据是否一致，未知项是否真的没有被写成事实。
- 覆盖矩阵是否遗漏用户明确关心的链路，`partial` 和 `unknown` 是否有可执行的下一步。
- 数据关系的键和基数、状态机的迁移、部署图的进程边界是否各自有实现依据。
- 桌面和 320px 手机截图中是否存在文字截断、控件重叠、不可读缩放或大面积无效留白。
