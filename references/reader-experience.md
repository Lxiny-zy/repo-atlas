# 交付给人阅读的报告

报告的目标是让读者理解业务与系统。字段格式、生成器能力和代码索引服务于这个目标。编写清单之前，先确定读者希望回答的问题，再组织内容。

## 阅读顺序

1. **项目全貌**：用一两句话说明服务谁、帮助完成什么事、最终留下什么结果。范围与环境限制放在可以展开的说明中。
2. **业务场景**：用“提交后会发生什么”“取消后数量去了哪里”等读者问题组织导航。先说明开始条件和结果，再逐步解释中间过程。
3. **重要结论**：直接说清已知行为、缺口以及它对业务意味着什么。结论标题应能独立读懂。
4. **协作关系**：图只表达正文需要的联系；节点使用业务职责，连线使用明确动词。
5. **源码依据**：需要核验时再展开文件、行号、函数和摘录。保持定位准确，不把技术标识当作故事主体。

不要为了隐藏技术词而删除必要条件、异常分支或未知项，也不要根据函数名自动编造业务意义。

## 各字段怎样写

| 内容 | 推荐写法 | 需要避免 |
|---|---|---|
| 项目摘要 | 谁发起什么动作，系统处理后得到什么 | 目录列表、技术栈清单、空泛“提供相关能力” |
| 模块名称 | 订单办理、商品库存、审核结果 | 直接把 OrderService、handler、worker 当作名称 |
| 模块说明 | 说明负责的事、接收的信息和交给下一环的结果 | “调用 X 函数，返回 Y 对象”的代码转述 |
| 流程标题 | 提交购买后会发生什么 | submitOrder 调用链 |
| 阶段标题 | 有货才预留，没有货就说明原因 | validate / execute / persist |
| 阶段正文 | 发生什么、何时继续、失败后怎样、改变了什么 | 只列函数先后，或只有“处理数据” |
| 发现标题 | 库存不足时，不会留下新订单 | 库存模块分析、某个方法行为 |
| 业务影响 | 顾客不会拿到一笔没有预留商品的新订单 | 只重复结论，或无依据地判断高风险 |
| 待确认项 | 指出尚不知道什么，以及从哪里继续核对 | “待完善”“进一步研究”等空话 |

技术名确实有助于定位时，可以在说明末尾括注，或留在源码依据、对象索引、接口索引中。标题和段落首句仍需讲清业务含义。对技术读者也应先给结论，再给实现依据。

## 表达约束

- 默认使用读者语言；中文报告避免无意义混用 authored relationship、hop、blast radius 等词。
- 首次使用事务、幂等、补偿等术语时，结合当前场景解释。例如“同一订单再次取消不会重复归还库存”，再按需注明幂等性。
- 代码只返回内存记录时，不写成“已入库”；只构造消息时，不写成“已送达”；没有支付证据时，不把创建订单称为“交易完成”。
- “有源码依据”与“已经人工复核”分别表达；证据数量或覆盖率不是系统质量分数。
- 稳定 ID、函数名和路径保持原值用于定位；显示标题单独使用有意义的业务措辞。
- 生成器不应通过正则替换函数名来假装理解业务。已有技术化清单需由阅读过源码的作者重写显示字段。

## 图形与移动端

每张图只回答一个问题。避免巨大总图承载所有链路；主流程先用可顺序阅读的文字讲清，图承担关系补充。节点标题不依赖悬停才能读懂，手机端重要说明不得缩成小字。

320px 下检查标题换行、正文阅读、折叠说明、导航、证据返回和未知项。读者应能从首页进入一个场景，读懂结果，再在需要时找到对应源码。

## 交付前的人工检查

只看首页和一个主要流程，不打开代码，尝试回答：

- 这个项目帮谁完成什么事？
- 从哪里开始，成功之后得到什么？
- 哪一步可能中断，发生后会怎样？
- 哪些内容已经有依据，哪些还不能确认？
- 如果我要验证一个结论，在哪里打开对应依据？

如果只能复述函数名或目录名，说明报告仍需重写表达。浏览器测试通过只证明页面可操作，不能代替这个阅读检查。

可参考 [订单业务阅读示例](../examples/order-journey/atlas.json)。示例基于同目录的合成源码，明确保留内存存储和支付/物流未覆盖等边界。
